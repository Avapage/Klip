# Release and signing guidance

Routine push and pull request checks build debug APKs and do not publish releases, overwrite release assets, or move tags. To ship, use a separate deliberate release process and a stable, privately backed-up signing key. Debug builds previously distributed may not update to the new signed build; removing an old installation also removes app data, but does not remove the user's saved Downloads files.

For a local signed build, securely provision KLIP_KEYSTORE_PATH, KLIP_KEYSTORE_PASSWORD, KLIP_KEY_ALIAS and KLIP_KEY_PASSWORD in the process environment and run `gradle :app:assembleRelease`. Store the keystore and recovery information outside the repository, with a secure backup. Do not put passwords or the keystore in the repository or logs. Verify the certificate and APKs with `apksigner verify --print-certs` and generate SHA-256 hashes. Keep a record of the source commit and test every APK before release. A release build without these settings is unsigned and must not be distributed as a signed build.

Use a fresh version code for installable updates and a new, unique tag for each immutable release. Never force-move a published tag or replace its APKs. Release publication is manual until a safe verified process and signing secrets are configured. Publish only the ARM64 and Universal APKs for future releases. Keep at most three subversions for each app version. Make all revision filenames and checksums distinct, identify the recommended one in the notes, and do not silently overwrite or remove previously published assets. If a fourth is required, publish a new app version rather than adding it to the existing one. GitHub may add source archive links automatically.

## One time signing setup

The owner should run `python scripts/setup_signing.py` on a trusted computer with JDK 17, Python 3, and GitHub CLI installed and authenticated to the repository owner. The script creates `~/KlipSigning/klip-release.p12` outside the repository, asks for a password without displaying it, and stops until the owner confirms a secure backup. It then sends the key and password to GitHub as Actions secrets. The owner must retain both the keystore and password in secure separate backups. Do not post them in chat, commit them, or upload them as release assets. The script refuses to overwrite an existing keystore. If interrupted after creating it, do not run keytool to replace it; use `gh secret set` to restore the same four secrets from the existing keystore and password.

After setup, an owner may manually run **Build signed Klip APKs** on the main branch in GitHub Actions. It produces four signed APKs and checksums as a temporary workflow artifact. The workflow does not publish or change a GitHub release. Inspect the signing certificate fingerprint, verify the APKs on devices, and publish individual APKs under a new version when ready. Existing debug installations signed with a different key require a one-time uninstall; Android removes app settings when uninstalling, while files in Downloads remain. Use the same signing key and increasing version codes for subsequent updates. Never regenerate a lost key as a substitute for a backup.
