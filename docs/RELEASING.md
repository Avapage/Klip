# Release and signing guidance

CI builds debug APKs only and never publishes releases, overwrites release assets, or moves tags. To ship, use a separate deliberate release process and a stable, privately backed-up signing key. Debug builds previously distributed may not update to the new signed build; removing an old installation also removes app data, but does not remove the user's saved Downloads files.

For a local signed build, securely provision KLIP_KEYSTORE_PATH, KLIP_KEYSTORE_PASSWORD, KLIP_KEY_ALIAS and KLIP_KEY_PASSWORD in the process environment and run `gradle :app:assembleRelease`. Store the keystore and recovery information outside the repository, with a secure backup. Do not put passwords or the keystore in the repository or logs. Verify the certificate and APKs with `apksigner verify --print-certs` and generate SHA-256 hashes. Keep a record of the source commit and test every APK before release. A release build without these settings is unsigned and must not be distributed as a signed build.

Use a fresh version code for installable updates and a new, unique tag for each immutable release. Never force-move a published tag or replace its APKs. Release publication is manual until a safe verified process and signing secrets are configured. Keep at most three subversions for each app version. Make all revision filenames and checksums distinct, identify the recommended one in the notes, and do not silently overwrite or remove previously published assets. If a fourth is required, publish a new app version rather than adding it to the existing one. GitHub may add source archive links automatically.
